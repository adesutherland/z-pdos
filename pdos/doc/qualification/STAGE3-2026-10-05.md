# Stage 3 CMS cREXX compatibility — local qualification, 5 October 2026

We implemented a bounded CMS MODULE environment in current z/PDOS source.
This is a source-built guest result, not a published image or general CMS
compatibility claim. At qualification time the checkout was `develop` at
`78a0651ae47868b6daf601fbb2ac6bdcb6eb9502`, with stage 3 changes
uncommitted. The guest was Hercules 4.9.1.0-SDL, one model-4381 z/Architecture
CPU, 4096 MiB, IBM1047 console 0009, 100-cylinder 3390 IPL disk 01B9 and a
separate checked CMS exchange disk 01BA. The host was macOS arm64, using the
current source image recipe, Mainframe Classic C 3.4.6, Apple Clang 21.0.0
and local cREXX beta 3. Build receipts pin the exact OS/runtime inputs.

## Binary and service boundary

The unchanged `CREXX-v1.0.0-beta.3-mainframe.zip` has SHA-256
`d5e2c8bca5f90d973c01e43a81483f4827fabe534b49417ca4f5508fdef97a3a`.
`cms.crexx inspect` pinned the CMS24 RXVM and CMS31 RXVM/RXAS/RXC MODULEs,
their record framing, entry/origin/end, flags and relocation counts in the
contract. `cms.crexx prepare` staged the original MODULE bytes and selected
fixtures on a fresh exchange CKD and verified its complete stopped-disk
readback. The contract and staging receipts are
`build/pdos/cms-module-contract-c.json` and
`build/pdos/cms-module-recipe-c/media/lock.json`. The CMS24 RXVM MODULE hash
is `cc407cf3efeae56cc9b4faea5be1cda972a3a6f7acd432af0534195f2d4d478f`;
CMS31 RXVM is `ab4559a827ade0769db7141b588540169c79a16939401e014cc52d027672ead0`.
The CMS24 MODULE has a fixed entry/origin `0x20000`, end `0x1ba6c0`, 27
records and no relocations. CMS31 RXVM has 70 records and 32,137 checked
relocations. These are original release binaries, not TSO rebuilds.

The host inspection pins the release ZIP by SHA-256 and verifies every selected
MODULE's bytes and records before staging. `CMS CHECK` then validates the
staged envelope, transfer digest, MODULE framing, addresses and relocation
forms in the guest; it is not a guest-side SHA-256 identity check. `CMS RUN`
dispatches CMS31 in relocatable AMODE31 application storage and CMS24 RXVM at
its checked fixed AMODE24 origin. The adapter belongs to `pdos/src/pdos.c`,
with the CMS31 FST veneer in `pdos/src/pdossup.asm` and the operator commands
in `pdos/src/pcomm.c`.

| Selected service route | Implemented requests in this source result |
| --- | --- |
| CMS31 CMSCALL, SVC 204 | `DMSFROSV`/`DMSFRRSV` storage, `LINEWRT`/`LINERD`, and `STATE`/`RDBUF`/`ERASE`/`WRBUF`/`FINIS` file requests. |
| CMS31 SVC 205 | FST lookup over `CMS31.` datasets on the selected exchange volume. |
| CMS24 SVC 202 | `TYPLIN`/`WAITRD` and the selected shared file requests, with its separate low-address parameter convention. |

File names map to `CMS24.` or `CMS31.` datasets on the selected exchange
volume. Output files are buffered when opened, then allocated and written on
`FINIS`. The service rejects out-of-profile address ranges, record sizes,
unsupported verbs and unavailable files; it does not validate ownership of
every mapped address. DIAGNOSE calls are outside this adapter and were not
qualified. The selected beta 3 workloads below establish only the observed
subset.

The fixed CMS24 image overlapped the inherited 0.5 MiB standalone stack.
The qualified bridge places the z/Architecture standalone stack in the
reserved 15–16 MiB system range while retaining the 2–3 MiB one-MiB kernel
image slot and a kernel heap starting at 3 MiB. The compiled `PDOS` structure
alone requests 8,806,400 bytes including alignment. A trial that moved the
heap to 8 MiB and the below-line application pool to 10–15 MiB booted PCOMM,
passed `CMS CHECK 24 RXVM`, then stalled at `CMS RUN 24 RXVM -v`. Its initial
kernel allocation could not fit in the 8–10 MiB gap, so the trial cannot
isolate an image-slot limit. It was reverted. Kernel growth and an above-line
body belong to
[PD-003](../BACKLOG.md#pd-003-shared-selectors-and-native-64-bit-kernel),
with below-line entry and channel-I/O resources retained and qualified.

## Post-review baseline

Source review corrected CMS31 `DMSFRRSV` so a release request cannot pass a
null, unallocated heap to `memmgrFree`. A separate boot guard now rejects an
initial kernel-table allocation that reaches the below-line application pool.
The latter protects the current placement but does not bound later standalone
heap growth. Both changes are part of this stage 3 source result.

The post-review image at `build/pdos/stage3-review-guard/media/pdos00.cckd`
has SHA-256 `500f27f543d38b406d3de32a10e7807cf345498ad7f55bedf646b54eb22a6278`.
Its 23-object build, loader checks and disk readback passed. A targeted guest
boot mounted the checked exchange disk, passed `CMS CHECK 31 RXVM` with 32,137
relocations, ran `CMS RUN 31 RXVM -v` at RC 0 with a 64 MiB storage request,
then exited PCOMM, reached enabled wait `0444` and stopped under the guest
fleet. The invalid release request itself was source-reviewed and built, not
invoked in the guest. Mainframe Lab retains the private
`stage3-review-20261005/result.json` receipt.

The final source build is `build/pdos/stage3-review-memory-guard`; its image
SHA-256 is `5858894fd4906b9785202796b740d11d7af5537b3c6c0e25a0b8b3d68d9ca7a9`.
It passed the same host image checks. The target compiler folded away the
current-layout boot guard: its PLOAD, PDOS and PCOMM linked program bytes are
identical to the targeted guest image above. The CCKD container bytes differ,
so this final container was not separately booted. The full CMS and TSO

## Later 0.1.1 operator acceptance finding

The 0.1.1 operator test exposed a shutdown gap in the stage 3 CMS24 evidence:
that run had reported PCOMM return 0 but had not observed the final wait. On
the first 0.1.1 candidate (`f2bd11161caa323904633d8a513631364eeb4ac0acd9afbac57c97024c7b3008`),
the operator's CMS31 and CMS24 workloads and stopped-disk output checks
passed. After `SELECT PDOS00`, `UNMOUNT CMSX01` and primary `EXIT` at RC 0,
Hercules remained running at PSW `0x3258`, then reported a program-interrupt
loop. The address maps into PLOAD's C exit routine. CMS24's checked fixed
image covers PLOAD's 1 MiB boot heap, so returning through that exit path is
unsafe once the kernel has run.

The z/Architecture kernel now enters its own `0444` wait after turning DAT
off. The focused repaired image (`662e54b3f41880d68dfd468dd32f20e7d829dbedb1e2a98f4c5c8e9b7fea6192`)
passed a fresh CMS24 IO24 automatic run at `PASS=6 FAIL=0 SKIP=1`, RC 0;
primary PCOMM returned 0 and Hercules observed enabled wait `0444`. This
targeted check establishes the shutdown repair. The subsequent full managed
guest acceptance is recorded in the
[0.1.1 operator record](0.1.1-OPERATOR-UAT-2026-10-05.md). The older 0.1
image remained selected while the repaired candidate was tested.

## Operator route and limits

From a checked release ZIP, run `crexx -nokeep pdos/scripts/cms.crexx --args
inspect ZIP SHA256 FRESH_ABSOLUTE_CONTRACT.json`, then `prepare ZIP CONTRACT
build/pdos/FRESH_WORK HERCULES_BIN`. Install the resulting exchange CCKD only
on a stopped disposable guest. In PCOMM use `MOUNT 01BA CMSX01`, `SELECT
CMSX01`, `CMS CHECK 31 RXVM` or `CMS CHECK 24 RXVM`, then `CMS RUN` with the
profile, program and native arguments. `HELP CMS` lists the supported forms;
long commands use the PCOMM `&`/`MORE>` continuation. On completion select
the IPL disk, unmount exchange, exit PCOMM, observe the wait and stop Hercules
before converting or checking written CKD bytes.

The CMS24 pass is the historical library-free RXVM IO24 subset. It does not
qualify a CMS24 compiler/assembler chain, arbitrary CMS command processor
functions, DIAGNOSE calls or native TSO24 execution. CMS31's frozen runtime
reports three deliberate automatic skips; CMS24's automatic run has one
input skip. The accepted managed `pdos` selection was restored to
`versions/zpdos-0.1`; its configuration again has only IPL disk 01B9. The
emulator and task leases were released. No stage 3 image was published.
