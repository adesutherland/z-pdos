# Phase 2 local media qualification, 4 October 2026

## Scope and inputs

This is a source-built, private guest check for the bounded phase 2 media and
fixture route in [PD-018, PD-019, PD-020 and PD-014](../BACKLOG.md). It is
not a release or CMS MODULE execution qualification. The base Git commit was
`f16eb35e849bbc97cc91073cefabfdaf81216662`; the phase 2 changes in this
record are uncommitted. The machine profile was one z/Architecture CPU,
4096 MiB, Hercules 4.9.1.0-SDL, 3390 CKD at `01B9` and `01BA`, and 3420
tape devices at `0560`–`0562`. The image recipe used the repository's built
Classic MVS C compiler, assembler and linker. `image.crexx` rebuilt 23 objects
and passed its loader, IPL-install, compression and whole-disk readback checks.

The broad guest run used `build/pdos/phase2-image-d-20261004` (CCKD SHA-256
`2bfbf703951d6919d8f0af7a7ac31d9246c1740ee5b387ccba89ebf051fa5de6`).
The follow-up from `d` to `e` changed only tape status/help wording and a
source comment.
`build/pdos/phase2-image-e-20261004` passed the same image checks (CCKD
SHA-256 `a621ef870b9aca2cef9c7d1630935aa4bf83ca08ab6b339f1665015ef09b7ec5`)
and booted for a final console check. All guest media were disposable or
read-only attachments; the accepted managed PDOS version was restored after
the run.

## Second disk

The disposable exchange volume had `VOL1` serial `EXCH01`, a VTOC, an 80-byte
`PROBE.DAT`, a native `OTHER.EXE`, and a preallocated 80-byte `OUT.DAT`.

| Guest action | Observed result |
| --- | --- |
| `VOLUMES` before mount | Only `01B9 PDOS00`, selected and IPL protected. |
| `MOUNT 01BB ABSENT`; `MOUNT 01BA WRONG1` | Both returned RC 8. |
| `MOUNT 01BA EXCH01`; duplicate mount | Valid mount returned RC 0; duplicate returned RC 8. |
| `SELECT EXCH01`; `DIR`; `TYPE PROBE.DAT` | Selection returned RC 0; prompt showed `EXCH01`; datasets were listed; fixture text was read. |
| `OTHER -C VERSION` | Native executable loaded from `01BA` and returned RC 0. |
| `COPY PROBE.DAT OUT.DAT`; `TYPE OUT.DAT` | Output read back as `PHASE 2 EXCHANGE DISK OK`. A first copy to a nonexistent `OUT.DAT` failed, establishing the current allocation limit. |
| `UNMOUNT EXCH01` while selected; then `SELECT PDOS00` and `UNMOUNT EXCH01` | Selected-volume unmount returned RC 8; selection and subsequent unmount returned RC 0. |

After a normal guest exit and Hercules stop, the exchange CCKD was expanded
to flat CKD and `OUT.DAT` was extracted from its VTOC extent. Its 80 bytes
matched `PROBE.DAT` and the source fixture exactly, SHA-256
`c29d8db008f70cff2e31703aa6be6228c1a4e017f54900df9fda417cb27c7a54`.
The IPL disk was also expanded before and after the run. All 85,248,000 CKD
track bytes matched exactly, SHA-256
`26590679f16de74aea661a1bac14d8ed468bc0a1b751ca59d4e28e7de6449a7a`.
The flat CKD utility header differed; it was excluded from the track-byte
comparison.

## Tape records

The CMS input was an unchanged VMFPLC2 HET image from the frozen beta 3
fixture set, attached read-only at `0560` (SHA-256
`11f4faae409cd9aa0542a4a21928bea3633fd2c597ad7c63f99efbc8e0c5f1ea`).
After `TAPE MOUNT 0560` and `TAPE REWIND`, guest `TAPE READ` reported the
first physical record as 77 bytes, FNV-1a 32 `4610D0D5`, with the same first
16 bytes as host `hetget`. The next record was 4,005 bytes, digest `6271DD7B`,
again matching host extraction. From after the first record, `TAPE SCAN`
reached a file mark after 4,941 more records and 19,735,681 bytes. Host
`hetmap` reported 4,942 blocks and 19,735,758 bytes for that file. Reading
after the mark returned zero length for the empty second file.

A separate standard-label AWS input at `0562` (SHA-256
`951885d63951bd2d2319448bc1587850218418ea8f905a03ce3ac5b75563699a`)
contained `VOL1`, `HDR1`, `HDR2`, a data file and EOF labels. The guest read
the 80-byte `VOL1` record with digest `C216402A`, scanned the two header
records to the first mark, read the 80-byte data record, crossed its file
mark, then read `EOF1`. This matched the host tape map. These are physical
record observations; z/PDOS did not decode standard labels or CMS VMFPLC2
content.

The writable output tape at `0561` was a separate initialized HET image.
`TAPE WRITE 00010203FEFF` and two `TAPE MARK` commands returned RC 0.
After rewind, the guest read a six-byte record with FNV-1a 32 `0D396C06`
followed by a zero-length file mark. After shutdown, `hetmap` showed one
six-byte block and two tape files; host extraction returned exactly
`00 01 02 03 FE FF`. A write request while the CMS input was registered
read-only returned RC 8.

The final image also exercised the native `TAP:` DD through PCOMM. After
registering `0561` read-only and rewinding it, `COPY TAP:0561 OUT.DAT`
allocated the tape DD and read one six-byte record followed by a file mark.
The fixed 80-byte `OUT.DAT` extracted from the stopped exchange disk began
with exactly `00 01 02 03 FE FF` and was zero-filled for the remaining 74
bytes. `TAPE OFF` and exchange unmount both returned RC 0 after the DDs
closed. This proves the small native read path, not arbitrary tape records or
larger tape records. A separate native write run used `COPY PROBE.DAT
TAP:0561` on a fresh writable HET. The guest reported an 80-byte write;
`TAPE MARK`, rewind and read returned the same 80-byte record (FNV-1a 32
`617ED856`) followed by a file mark. After shutdown, host extraction matched
the source `PROBE.DAT` exactly, SHA-256
`c29d8db008f70cff2e31703aa6be6228c1a4e017f54900df9fda417cb27c7a54`.

## Final console and boundary

The final `e` image booted to PCOMM. `HELP` displayed the tape commands
legibly, `VOLUMES` returned the protected IPL volume at RC 0, `TAPE STATUS`
reported `off` at RC 0, and an invalid `TAPE BAD` returned a readable two-line
usage message with RC 8. PCOMM exited, Hercules reached its `0444` wait,
`stopall`/`quit` completed, and the shared guest was left stopped with its
accepted `zpdos-0.1` version and original Hercules configuration restored.

The later final `h` image also rejected `TAPE READ` before registration and
`TAPE MOUNT 0563` for an unattached device, each at RC 8. It registered the
unchanged standard-label AWS at `0560` read-only, rewound and read its first
80-byte `VOL1` physical record at RC 0, then released the tape. The guest
FNV-1a 32 value `AA6CED59` matched host decoding; the tape SHA-256 remained
`120f1a103b2b29c71726f36259fe689a410225b9ee1070c92277f2eea621910c`.

The initial `e` image transported CKD datasets and raw tape records. The
subsequent `f`, `g` and `h` images added allocation and checked fixture
exchange, as qualified below. CMS MODULE execution is a separate phase 3
item. Larger native `TAP:` DD reads or writes have not been qualified; the
raw tape buffer is 32,767 bytes per record.

## Guest allocation and write failure

The `f` image was freshly built from 23 objects and passed image/loader and
whole-disk host controls. On a disposable `EXCH01` exchange disk, `ALLOC
OUT.DAT FB 80 80 1` reported `cyl=5..5` and RC 0. `COPY PROBE.DAT OUT.DAT`
then wrote the 80-byte fixture. After guest stop, the output DSCB was at
VTOC record `1/0/5` with extent `5/0..5/14`; its 80 bytes exactly matched
the input, SHA-256
`c29d8db008f70cff2e31703aa6be6228c1a4e017f54900df9fda417cb27c7a54`.
Duplicate `ALLOC`, invalid VB geometry and an IPL allocation request returned
RC 8. `HELP` listed `ALLOC`.

The final `h` image changed only invalid-request diagnostics after the `g`
guest success below. It again passed the 23-object host image and loader
controls (CCKD SHA-256
`b1874d519aa6bd8ffe5617df31ea99218005e3deb07cb216b81620dadc0a6bce`). A disposable exchange
disk was attached through Hercules' CKD `ro` option. `MOUNT` and `SELECT`
succeeded; `ALLOC FAIL.DAT FB 80 80 1` reported inability to initialize its
data extent and RC 12. `DIR` did not list `FAIL.DAT`; after shutdown the
exchange CCKD SHA-256 was identical to its untouched input,
`8d3b8c185dfef702a8b32c0f882734af253276d5b0c352918c8aa03a3b57388c`.
Invalid VB geometry on this final image gave the readable RDW/BDW diagnostic
and RC 8. The controlled fault covers refusal before DSCB publication; a
late VTOC write fault and rollback under persistent device failure were not
injected.

## CMS and TSO fixture round trips

The `g` image passed the fresh 23-object host image and loader controls; its
IPL CCKD SHA-256 was
`b4917fade7611cf336ed2c265ca31c0a6429bd4d5d3de058d539901f858a165a`.
The product [`fixtures.crexx`](../scripts/fixtures.crexx) recipe validated a
ZIP and its unchanged tape members, built a fresh `FIXT01` exchange CCKD,
read back the full CKD track payload, and generated the guest command list.
The synthetic CMS VMFPLC2 HET SHA-256 was
`47c1715cb80d54fae34a6a9b8451c29d29f81f95e2c32e38d670b4ebac0ee850`;
the synthetic standard-label AWS SHA-256 was
`120f1a103b2b29c71726f36259fe689a410225b9ee1070c92277f2eea621910c`.
They were kept unchanged in the ZIP (SHA-256
`cc3853a98f2b8fec54a9b934a67aa8b0fa9bf821775947f0e47f785bafd6103d`).

An initial guest attempt used ordinary byte-stream `COPY`. It preserved CMS
text, the 00–FF binary record and TSO fixed records, but dropped a sole
zero-length CMS variable record. This is why the bounded, record-preserving
`RCOPY` command was added. A fresh guest then ran all 12 generated mount,
select, `ALLOC`, `RCOPY`, return and unmount commands with RC 0. The stopped
disk exporter compared each ordered record and exact binary byte:

| Source | Guest output | Records | Result |
| --- | --- | ---: | --- |
| CMS variable text with an empty middle record | `CMT.OUT` | 3 | Exact logical records and bytes |
| CMS sole zero-length variable record | `CMB.OUT` | 1 | Exact record count and framing; payload is zero bytes |
| CMS variable binary `00` through `FF` | `CMBIN.OUT` | 1 | Exact 256 bytes, SHA-256 `40aff2e9d2d8922e47afd4648e6967497158785fbd1da870e7110266bf944880` |
| z/OS standard-label FB80 text and blank record | `TSO.OUT` | 2 | Exact 160 bytes and record boundaries |

The source-built `run` recipe itself was then exercised from a fresh IPL:
all 12 commands reported PASS in order. Its stopped-disk `verify` produced
four exports with matching record and payload hashes. The tightened verifier
also compared all unrelated CKD tracks and unchanged VTOC records against the
prepared baseline; they were identical. The IPL disk's 85,248,000 track
bytes were identical before and after the `g` guest run.

Host negative controls changed one field at a time in a disposable manifest:
archive SHA-256, tape SHA-256, standard-label dataset name and logical-record
SHA-256. All four were rejected before an exchange candidate existed. The
initial byte-stream `COPY` result was rejected by stopped-disk verification
because the sole empty record was missing.
The operator `inspect` step was checked with a zero-hash draft of the same
ZIP and tapes; it generated a pinned manifest whose archive, tape, record and
payload hashes matched the independently prepared qualification manifest.

Finally, the same recipe imported `IOBAD CREXX` as four CMS variable records
from the **unchanged beta-3 CMS31 distribution HET**, SHA-256
`11f4faae409cd9aa0542a4a21928bea3633fd2c597ad7c63f99efbc8e0c5f1ea`.
A fresh guest ran its six mount/select/allocate/record-copy/return/unmount
commands at RC 0. Stopped-disk export matched all four records and binary
bytes, record SHA-256
`2e5402d4712cd04eb9dfab8f379afa1d96f71c451276abd00ce885f5ce342ec8`;
the stricter unrelated-track and VTOC check passed. The tape image bytes were
unchanged. This is release-fixture transport and readback evidence; the CMS31
programs on that tape were not executed on z/PDOS.

Every guest in this record exited PCOMM and Hercules normally, released its
console, device and emulator leases, and left the managed PDOS stopped with
the accepted `zpdos-0.1` image and original Hercules configuration selected.
